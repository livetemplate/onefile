# Plan: a db onefile app, with saved queries and a Run button

State — Done: plan (#16); Phase 1 in [tinkerdown#389](https://github.com/livetemplate/tinkerdown/pull/389), released in v0.10.0; Phase 2's audit. Next: Phase 2's build.

## Context

The next app is `db`, second on the [roadmap](../ROADMAP.md) and the top one not built. It lists the queries in your `.sql` file, each with a Run button, and shows the result as your database's own command-line client prints it. Editing the file updates the list. SQLite and Postgres come first.

One rule from review shapes the design: tinkerdown reads a `.sql` file and understands it, the way it reads a `.http` file (user, 2026-11-25). So the queries live in a file in your repo, and a command you pass runs the one you click. The app follows the [http app](2026-11-22-http.md): a list a file feeds, and a pane a click fills.

`-- name: NAME` is the header developers already use to name the queries in a `.sql` file:
- [sqlc](https://docs.sqlc.dev/en/latest/reference/query-annotations.html) writes `-- name: GetAuthor :one`.
- [aiosql](https://nackjicholson.github.io/aiosql/defining-sql-queries.html) writes `-- name: get-users`, with an optional operator after the name, such as `^` or `!`.
- [yesql](https://www.npmjs.com/package/yesql) uses the same header, and [HugSQL](https://github.com/layerware/hugsql) writes `-- :name update-name :!`.

The four were found by a web search of their docs, 2026-11-25.

The audit (2026-11-25, sqlite3 3.45.3 and psql 15.20, in Docker) settled these facts:
- `sqlite3 -box DB "SQL"` prints a box-drawn table per statement, and nothing for an empty result, with exit 0. NULL prints as an empty cell.
- `-readonly` refuses a write with `Runtime error near line 1: attempt to write a readonly database (8)`, exit 1. sqlite3 3.51 prints `Error: stepping, attempt to write a readonly database (8)` and exits 8, so a test checks for `readonly database`, not the whole line. A missing database file is an error, not a new file.
- SQL piped to `sqlite3` runs dot-commands: `.shell echo X` ran. `-safe` refuses `.shell` and `ATTACH`, from stdin or as an argument.
- `psql -X -v ON_ERROR_STOP=1 -c "SQL"` prints an aligned table per statement with a `(N rows)` footer. Text piped to stdin runs meta-commands. So does `-c` when its text is one backslash command: `-c '\! echo X'` ran on psql 13 and 16 (2026-11-26), because `-c` takes SQL or a single backslash command. With a leading space, `-c ' \! echo X'` goes to the server and is a syntax error.
- `PGOPTIONS='-c default_transaction_read_only=on'` refuses `DELETE` with `cannot execute DELETE in a read-only transaction`. With `-c`, as the README runs it, psql 13, 14 and 16 exit 1. A query that starts with `SET default_transaction_read_only=off` gets past it.
- tinkerdown can't read a `.sql` file. That's Phase 1. The click, the private value and the response pane exist already, from the http app.

## Product

| User journey | What they see | Built on |
|---|---|---|
| See my queries | one row per query: its name, its first keyword, and its first line of SQL | `--source sql:./queries.sql`, or `sql:./queries/` for a folder of `.sql` files (Phase 1) |
| Edit a query | the list follows the files; a deleted query or file leaves | the `.sql` reader re-reads a file, or the folder, when it changes (Phase 1) |
| Find a query | the search box narrows the list by name and SQL | an `f.fields.text` filter, as http's |
| Run one | **Run** on the row; the pane shows ● running, then the result | a merge with `on: execute` starting `--source run=` |
| Read the result | the client's own table, one line per row, in monospace; "No rows" for an empty result | `sqlite3 -box`, `psql` aligned output |
| See why it failed | the client's error, marked as stderr, and its exit status | `stream: stderr`, the `system` row |
| Spot a query that writes | its keyword (`update`, `delete`…) is marked; the read-only connection refuses it | the row's `kind` (Phase 1), `-readonly` and `PGOPTIONS` |
| Browse a table | a query in the file, such as `SELECT * FROM users LIMIT 100` | the same Run |

## What the code looks like

The serve commands, as the README will publish them. Users copy these, so they're the app's contract:

```sh
# SQLite
tinkerdown serve --allow-exec github.com/livetemplate/onefile/db \
  --source sql:./queries.sql \
  --source 'run=sqlite3 -safe -readonly -box ./app.db " $TD_sql"'

# Postgres: the connection comes from PGHOST, PGDATABASE, ~/.pgpass and the like, never a password in the line
tinkerdown serve --allow-exec github.com/livetemplate/onefile/db \
  --source sql:./queries.sql \
  --source 'run=PGOPTIONS="-c default_transaction_read_only=on -c statement_timeout=30s" psql -X -v ON_ERROR_STOP=1 -c " $TD_sql"'
```

Both commands put a space before `$TD_sql`. psql runs `-c` text that is one backslash command, such as `\! rm …`, and the space sends it to the server instead, where it's a syntax error.

sqlite3 reads an argument that starts with `-` as an option, so a query that starts with a `--` comment fails with `unknown option`. A `--` before the query would fix that only from sqlite3 3.45: 3.40.1 and older reject `--` itself. The space also turns a query that starts with `.`, a dot-command, into an SQL syntax error.

The page's sources. The merge is named `list`, not `queries`, because `--source sql:./queries.sql` is labelled `queries`. A clash renames the source to `queries-2`, and the entries read `queries-2/1`. The audits can change the details:

```yaml
sources:
  list:
    type: merge
    inputs: ["*"]
    key: [fields.entry]
    accepts: {kinds: [sql], min: 1, hint: "--source sql:./queries.sql; see the README"}
  result:
    type: merge
    inputs: [run]
    on: execute
    buffer: 5000
    line_max: 1MiB
    params:
      entry: {in: list.fields.entry}
```

A row's markup: `<li data-key="{{.key}}" class="kind-{{.fields.kind}}">`, with `<button name="execute" data-entry="{{.fields.entry}}">Run</button>`. The button is named `execute` because `run` is a built-in action, which never starts an `on:` merge.

Phase 1 adds a `sql:PATH` input, like `http:PATH`, where PATH is a `.sql` file or a folder of them. It's for `--source` flags and for a `sql:` key in a config file. Each query becomes a row with the fields in § Contract, and its SQL reaches a clicked command as `TD_sql`.

## Decisions

- Queries come from a `.sql` file that tinkerdown reads, not from a box you type in.
  alternative: a query box, with a new kind of click value that takes typed text
  because: the user asked for a file tinkerdown understands (2026-11-25). A file also keeps queries in git, as the `.http` file keeps requests
- A query starts at a `-- name: NAME` line, or HugSQL's `-- :name NAME`, and runs to the next one. NAME is the first word after the header. A word after it, such as sqlc's `:one`, and trailing operator characters (`^ $ ! < * #`), as aiosql and yesql write them, are dropped from the name.
  alternative: split the file at each `;` that ends a line
  because: a `;` can sit inside a string or a function body, and a name gives the row its label
- A file with no header is one query, named after the file: `users.sql` is `users`. It's the classic layout of one query per file (user, 2026-11-25). In a file with headers, text before the first one, and a header with no SQL under it, are skipped.
  alternative: refuse a file with no header
- `sql:` takes a file or a folder, and a page takes several: `--source sql:./users.sql --source sql:./reports/`. A folder gives each `*.sql` file in it, not its subfolders, in name order, and a file there is read as above (user, 2026-11-25).
  alternative: one `sql:` source per page
- A row's `entry` starts with its source's name, as in `users/1`. So a click runs the query it shows, whichever file holds it. The `.http` reader gets the same `entry`, as in `api/1`.
  alternative: number entries from 1 in each source, as the `.http` reader does today
  because: a click runs the first row whose `entry` matches (`clickEnv` in `internal/source/stream.go`). With two files, Run on the second file's first query would run the first file's. http has this bug today, and its README says to pass one `--source` per file
- `kind` is the query's first SQL keyword, lowercased, after comments. tinkerdown doesn't judge whether a query writes: the page marks the kinds, and the read-only connection refuses a write.
  alternative: a `writes` flag tinkerdown sets
  because: `WITH … DELETE` and `PRAGMA` make a keyword list wrong in both directions, and the database knows for sure
- Browsing a table is a query in the file. The page has no table list.
  alternative: a table pane, fed by a second command that lists tables
  because: one pattern, and the file is where the user already writes what they want to see
- The result is the client's own text, one line per row, not parsed into cells.
  alternative: JSON output parsed into a table (`sqlite3 -json`, `row_to_json`)
  because: `sqlite3 -json` prints one array over many lines, and psql has no JSON output for any query. The client's table is also what users read in a terminal
- The SQL reaches the command as `$TD_sql` in its arguments, never on stdin.
  alternative: `printf "%s" "$TD_sql" | sqlite3`, as http pipes headers to curl
  because: piped SQL runs the client's meta-commands (`.shell`, `\!`). An argument with a leading space runs none, on psql and on sqlite3
- The README's commands are read-only: `sqlite3 -readonly` and `PGOPTIONS=default_transaction_read_only=on`. Writing is the user's choice, by changing the command.
  alternative: writable by default, with a confirm on write kinds
  because: a page is for looking. The read-only flag turns a mistaken Run on `close-stale` into an error, not a change
- The SQL also shows in the row, as `fields.sql`. It is still passed privately, as `TD_sql`.
  alternative: keep it private like http's body
  because: the user should see what Run will do, and the file is theirs. It goes privately because a query can be many lines and over 256 bytes

## Security

- **What runs:** the user's `run` command, once per click, with the clicked query's SQL as `$TD_sql`. It can change data when the query writes and the command isn't read-only, so the README's commands are.
- **Values from the browser:** only `entry`, checked by `in: list.fields.entry`. The SQL comes from the file on the server and is never sent by the browser.
- **A hand-made message or a replayed URL:** at most a query in the file runs, as a click would. `on: execute` means no URL or reload starts one.
- **Secrets:** results reach the page, its WebSocket frames and screenshots. The connection's password never does: it comes from `~/.pgpass` or the environment, not the command line, where `ps` shows it.
- **Untrusted text:** result cells and the SQL text are the database's and the file's, and are shown as text.
- **The README must warn:**
  - A `.sql` file runs as you, so run only files you'd run in your terminal.
  - Read-only guards against mistakes, not against a query written to get past it: Postgres lets a query `SET default_transaction_read_only=off`. For a real limit, connect as a role that can only read.
  - A result can show any data the connection can read.

## Contract

A query row's fields, with `msg` set to the name:
- `entry`: the source's name, `/`, and the query's place in it: `users/1`, `users/2`… across a folder's files
- `file`: the file's name, for a folder
- `name`
- `kind`: the first keyword, lowercased, such as `select`, `with`, `insert`, `update`, `delete`, `create`, `alter`, `drop`, `explain` or `pragma`; any word a query starts with
- `sql`: as written, trimmed
- `line`: the header's line number, or 1
- `text`: name and SQL, for search

Private value: `sql`, reaching the command as `TD_sql`, up to 128 KiB like http's values.

Click: `<button name="execute" data-entry="…">`. Defaults: a file or folder is read again when it changes. A file, or a folder's files together, hold at most 4 MiB, as a `.http` file does, and a folder holds at most 1,000 `.sql` files.

## Phases

### Phase 1: `.sql` files (tinkerdown)

- Audit: trace `http:PATH` from `parseSourceFlag` through `InputSpec.HTTP`, `readHTTPOnce` and `Hub.Private` to `TD_body`, and list each place that names the `http` kind.
- Implementation: per the tinkerdown Files list. **User contribution:** `queryKind(sql string) string` in `sqlfile.go`, 5–10 lines. It decides what counts as the first keyword: skip `--` and `/* */` comments, and choose whether `WITH` stays `with` or looks past the CTE.
- Acceptance: the tinkerdown criteria, then a release through `release.sh`.
- Learn:
  - `run` is a built-in action, so a button named `run` never starts an `on: run` merge, and the click failed without a clear error. Validation now refuses an `on:` named after a built-in, and the page uses `on: execute`.
  - A folder's modification time changes only when a file is added or removed, not when one is edited. So the reader compares each file's size and modification time.
  - The 4 MiB cap is for a folder's files together, not each file, so one read holds at most 4 MiB.
  - `file` is set on every row, not only for a folder, so a page never shows an empty field.
  - `queryKind` returns `with` for a query that starts with a CTE (written by Claude at the user's request, 2026-11-26).
