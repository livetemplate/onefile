## Context

The next app is `http`, first on the [roadmap](../ROADMAP.md) because HTTP clients are its most-starred job, and the big ones ask for an account and workspaces before the first request. It lists the requests in your `.http` file, each with a Send button, and shows the response: status line, headers, time, and the body, indented when it's JSON. Editing the file updates the list.

`.http` is the format developers already keep requests in. The VS Code REST Client reads it (7.8M installs), every JetBrains IDE has it built in, and httpyac and rest.nvim read it too. Hurl's format (19k stars) is read by Hurl alone (VS Code Marketplace and GitHub, checked 2026-11-22).

Three rules from review (user, 2026-11-23) shape the design: one file, tools already on the machine, and tinkerdown never sending HTTP. So curl sends, and tinkerdown reads the `.http` file and starts curl. The rules now apply to every app ([plans/README.md](README.md#rules-every-app-follows)).

The audit (2026-11-22, curl 8.18.0) settled these facts:

- `curl -w '%{json}'` prints one JSON line with `http_code`, `method`, `http_version`, `content_type`, `size_download`, `time_total` in seconds, `url_effective`, `exitcode` and `errormsg`. It needs curl 7.70 (2020); `exitcode` needs 7.75 (2021).
- `curl -i` prints the status line and response headers before the body. `-H @-` reads headers from stdin, one per line (curl 7.55).
- In `sh`, `${TD_body:+--data-binary "$TD_body"}` gives curl two arguments when there's a body, newlines kept, and none when it's empty. So a GET sends no body.
- tinkerdown can't do three things this app needs (Phase 1):
  - It can't read a `.http` file.
  - It has no run that only a click starts. A `params` merge starts as soon as the URL holds its values, so reloading, Back or a shared link would send a POST again.
  - A command gets only the button's values, each at most 256 bytes on one line, so it can't get a request's headers and body.

## What the code looks like

This section is a sketch: the audits can change the details. The app is the serve command and the page; tinkerdown's three features follow.

### The serve command (in `http/README.md`)

```sh
tinkerdown serve --allow-exec https://raw.githubusercontent.com/livetemplate/onefile/main/http/index.md \
  --source 'api=http:./api.http' \
  --source 'send=printf "%s" "$TD_headers" | curl -sS -i --max-time 30 -X "$TD_method" -H @- ${TD_body:+--data-binary "$TD_body"} -w "\n%{json}\n" -- "$TD_url"'
```

`api.http` is the user's file. tinkerdown sets the `TD_` values from the clicked request, with its variables filled in.

The same sources can live in a config file of the user's own instead, so the long command needs no shell quoting. tinkerdown already supports this: a page from a URL reads the sources in the file `--config` names (`remoteConfig` in `cmd/tinkerdown/commands/remote_page.go`). A throwaway chromedp check on 2026-11-23 served the `logs` page from its raw GitHub URL with a `--config` command source, and its line reached the page. Phase 1 adds `http:` as a config key beside `cmd:` and `file:`.

```sh
tinkerdown serve --allow-exec https://raw.githubusercontent.com/livetemplate/onefile/main/http/index.md --config http.yaml
```

```yaml
# http.yaml
sources:
  api:  {type: stream, http: ./api.http}
  send: {type: stream, cmd: 'printf "%s" "$TD_headers" | curl -sS -i --max-time 30 -X "$TD_method" -H @- ${TD_body:+--data-binary "$TD_body"} -w "\n%{json}\n" -- "$TD_url"'}
```

The page's CSS (not shown) does three jobs:
- The summary row, the one with a `fields.http_code`, moves to the top with `order: -1` and shows only its time. Every other row shows only its line.
- It resets tinkerdown's level colours inside the pane, since a body line holding "error" isn't a log level.
- It lays the response pane beside the list on wide screens, as `containers` does.

The `{{if}}`s sit outside the ranges, so every row in a range uses the same markup.

### tinkerdown (Phase 1)

- **The `.http` reader:** `--source NAME=http:PATH` reads the file whole, and again whenever it changes. Each read replaces the input's rows. Each request becomes a row with these `fields`:

  | Field | Value |
  |---|---|
  | `entry` | its position as a string, `"1"` first |
  | `name` | from `###` or `# @name` |
  | `method` | `GET` for a bare URL |
  | `url` | as written |
  | `headers` | one per line |
  | `body` | as written |
  | `text` | name, method and URL, for search |

  Fields keep `{{name}}` as written. The values with variables filled in are the row's private values (`Hub.Private`, keyed by its `seq`), which never enter template state (A2).
- **Click-started runs:** `SourceConfig.On string` (`yaml:"on"`), next to `Params`. The WebSocket action handler checks a map of `on` names before the action runner. On a match, it checks the button's values with the merge's params rules and finds the row they name. It then calls `hub.Restart` with `TD_<param>` plus that row's private values as `TD_method`, `TD_url`, `TD_headers` and `TD_body`. `Restart` kills the old process group, empties the buffer, and starts the inputs once.
- **Display and line length:** a `jsonindent` template function, and `line_max` on merges.

## Decisions

- Requests live in the user's own `.http` file, passed as a flag. The page holds no requests.
  alternative: requests written into the page
  because: a page served from its URL can't read files, and the user's file stays theirs in git
- The file format is `.http`.
  alternative: Hurl, Bruno's `.bru`, Postman collections, a file of curl commands
  because: it's the text format most developers already have, and the same file keeps working in their editor
- curl sends, from a `--source` flag. tinkerdown reads the file and starts curl, and never opens a connection itself.
  alternative: tinkerdown sends through its `rest` client; a downloaded `http.sh` that parses with awk and runs curl
  because: sending HTTP is not tinkerdown's job (user, 2026-11-23), and a second file breaks the one-file rule (user, 2026-11-23)
- tinkerdown gets a `.http` reader, `--source NAME=http:PATH`, a new flag kind beside `file:PATH`. It re-reads the whole file when its size or modification time changes, checked every 250 ms like the file tailer. Each read replaces the input's rows, so a deleted request leaves the list and the page gets a remove for it.
  alternative: a command printing JSON snapshots, and a generic "array line replaces rows" rule
  because: without a script, no command already on the machine can parse `.http`
- The `.http` subset: `###` separates requests, and text after it names the request. `# @name x` also names it. `#` and `//` start comments. The request line is `METHOD URL`, or a bare URL for GET, with an optional `HTTP/1.1` that's ignored. Headers run to the first blank line, and the body runs to the next `###`. `@name = value` lines define variables.
  alternative: none considered
- `{{name}}` takes the file's `@name` value, and `{{$processEnv NAME}}` the environment variable `NAME`. A plain `{{name}}` never reads the environment. tinkerdown fills variables into the row's private values only, so a token never reaches template state or the browser. A request with an unset variable gets no private values, and Send shows "unset variable name" without starting curl.
  alternative: fill variables into the shown fields; JetBrains' `http-client.env.json` environments; a plain `{{name}}` falling back to the environment, as Phase 1 shipped
  because: a shown token can end up in a screenshot or a shared screen. A fallback lets a file read any server variable it names, such as `{{AWS_SECRET_ACCESS_KEY}}`, and REST Client doesn't do it, so a file that works in VS Code would behave differently. Environment files are JSON with named environments, a feature of their own (G1)
- A file that doesn't parse shows the error with its line number in `.Error`, and the last good rows stay.
  alternative: none considered
- A link or URL never sends a request. Only a click on Send does.
  alternative: a `params` merge with `?entry=N`
  because: a URL is replayed by reloads, Back, Forward and shared links, which would send a POST or DELETE again
- tinkerdown gets a generic click-started run: `on: NAME` on a merge with `params`. A click on a button named NAME takes its `data-*` values as the params, checked by the same rules and `in` as URL values. It then clears the merge's rows and starts its inputs.
  alternative: an `--action` whose output shows on the page
  because: `--action` has a 30-second timeout and keeps no output. A merge already streams, buffers and shows rows, and `tasks` (roadmap #4) needs the same run started by a click, including runs that take minutes
- A click-started run also gets the private values of the row its params name in the `in` merge, as `TD_` values. These values can be multi-line and up to 128 KiB, unlike button values, because they come from the server's own rows, not from the browser. 128 KiB is Linux's limit for one environment string (`MAX_ARG_STRLEN`). A longer value, or one holding a NUL byte, refuses the run with a message naming the field (G3).
  alternative: pass headers and body as button `data-*` values
  because: those come from the browser, so they keep the 256-byte, one-line limit, and a hand-made message could set any header
- A click-started input runs once: it isn't restarted when it exits, and has no timeout. A click while it runs kills its process group and starts again. The block's `.Running` is true while it runs.
  alternative: refuse a click while running
  because: a hung request would otherwise need a page reload to retry; `tasks` needs restart too. curl's `--max-time 30` ends a request that hangs
- Each connection shows the run of its own last click. Runs are shared by values, as `params` buffers are today, so two tabs sending the same request see one run.
  alternative: one run per connection
- The response is `curl -i`'s output, then `-w "\n%{json}\n"`'s summary line. The leading `\n` keeps the summary off a body's last line when the body has no trailing newline.
  alternative: `%{header_json}`; a temporary file for the body
  because: `-i` shows headers as curl prints them, in one run. A body file needs `mktemp` and cleanup in the flag
- A merge gets `line_max`, defaulting to 16 KiB. `response` sets 1 MiB, so a minified JSON body arrives as one line.
  alternative: raise the cap for every stream
  because: the cap protects log streams from one huge line; only this merge expects one
- tinkerdown gets a `jsonindent` template function: it indents a string that parses as a JSON object or array and returns any other string unchanged.
  alternative: `jq` in the flag
  because: jq isn't on most Linux systems by default
- The page uses one row markup for the summary and body lines. CSS hides the parts that don't apply, using `data-exit` from `fields.exitcode`, which only curl's summary line has (A6).
  alternative: `{{if}}` per row
  because: a per-row `{{if}}` ends row-by-row updates ([pitfalls](README.md#pitfalls-found-so-far))
- The README gives both forms: flags, and a `--config` file with the same sources. The config file is the user's own, like `api.http`, so the app is still one download.
  alternative: flags only
  because: a command with nested quotes is easier to read and edit in YAML than in shell quoting (user, 2026-11-23)
- One `api`/`send` pair per file. Several files need several pairs.
  alternative: a list across files
  because: an entry number counts within one file; several files can come later if asked for

## Security

- **What runs:** `api` reads only the file its flag names. `send` runs curl with a request from that file, so it can send any method the file holds, including POST and DELETE. The page has no `--action`.
- **Values from the browser:** only `entry`, checked by `in` against the `requests` rows. The method, URL, headers and body come from the server's own row, never from the browser. A hand-made message can only send a request already in the file.
- **Replayed URLs:** a reload, Back or shared link sends nothing, since only a click starts `send`.
- **Secrets:**
  - Variables are filled in only in the row's private values, so a `{{token}}` value never reaches template state, a WebSocket frame or the HTML (A2).
  - A header written out in the file, rather than as `{{name}}`, shows on the page, and so do response headers and bodies, such as `Set-Cookie`.
  - curl gets headers on stdin, but the URL and body as arguments, which other users of the machine can see in `ps` (R2).
  - Without `-L`, curl doesn't follow redirects, so an `Authorization` header never goes to another host.
- **Untrusted text:** response headers and bodies, rendered as escaped text after `jsonindent` and `linkify`. `linkify` links only `http://` and `https://` URLs (`urlCandidate` in tinkerdown's `internal/server/linkify.go`), so a `javascript:` URL stays text.
- **README warnings:** write tokens as `{{$processEnv NAME}}`, and responses can show secrets.

## Constraints

- The serve command needs only `sh` and `curl`, beyond the rules in [plans/README.md](README.md#rules-every-app-follows).

## Contract

The row from the `.http` reader: `fields` `{entry, name, method, url, headers, body, text}`, all strings; private values (`Hub.Private`, keyed by `seq`) `{method, url, headers, body}` with variables filled in.

The click: `<button name="send" data-entry="{{.fields.entry}}">`. The command gets `TD_entry`, `TD_method`, `TD_url`, `TD_headers`, `TD_body`.

Defaults: re-read check every 250 ms, `--max-time 30`, a 5,000-row response buffer, `line_max` 16 KiB unless set, 1 MiB for `response`, 128 KiB for a private value.

- Acceptance: the tinkerdown criteria above. Release through `release.sh`.
- Learn:
  - A2 was false: see the tracker. A row's private values are a generic hub feature (`Hub.Private`), so the click passes each as `TD_<key>` without knowing about HTTP.
  - A manual input must never start on attach, including after an idle stop, or a reload would resend a POST. Only `Hub.Restart` starts one. Each run's context drops its late rows under the hub lock.
  - For a page from a URL, relative `file:` paths in flags pointed into the page's temporary directory, an existing bug. `http:./api.http` would have hit it, so flags now resolve from the directory `serve` runs in, and a `--config` file's paths from its directory.
  - Each click's values make their own buffer, which can hold a 128 KiB body. Idle click buffers now leave the hub, found by `/simplify`.
  - The PR review found three gaps, fixed in a follow-up. A plain `{{name}}` fell back to the server's environment; it now reads it only as `{{$processEnv NAME}}` (see Decisions). Comments between headers failed as "not a header". Clicks sent in a loop restarted the command each time, so a click within 250 ms of a page's last run now waits for the gap, and the last such click still runs. Dropping those clicks instead lost a real one in the e2e test, where a fast request finished and the next click came 224 ms later.
